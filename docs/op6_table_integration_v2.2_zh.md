# OP6 表格整合与拆分（V2.2 增补）

修订标识：`2.2-op6-v2`。保留 J1–J4，增加 J5–J7；不更名既有 Case ID，不删除 OP7。
本文与机器可读 Schema、`examples/op6_contracts.json` 一起用于新增案例标注。
构造示例仅展示标注规则，不是新增已发布案例，也没有新增模型评测成绩。

## 1. 测量对象与边界

OP6 将多个逻辑表按关系或共同 Schema 整合，或把一个逻辑表按明确规则分解为多个表，
核验匹配关系、记录出现次数、字段去向和信息覆盖。默认可在同一 `input.xlsx` 的多个 sheet/数据块中构造，
输出仍为一个 `submission.xlsx`。使用多个输入文件时，Harness 必须先显式支持并隔离挂载全部输入。

| 目标变化 | 标签 | 判定依据 |
|---|---|---|
| 按键把销售表和成本表横向关联 | OP6 J1–J4 | 关系键、连接基数和匹配策略 |
| 多地区同类明细纵向汇总为一表 | OP6 J5 | 按字段含义对齐后保留记录多重集合 |
| 按地区/期间把一张表分成多个表 | OP6 J6 | 每条记录的路由与覆盖 |
| 按字段组拆为维度表和度量表 | OP6 J7 | 保留共同键及可重组的信息 |
| 展开/重建合并单元格或层级表头 | OP7 | 单元格/层级关系表示变化 |
| 将年份列变为 Year/Value 记录 | OP1 | 宽长表或维度重组 |
| 把一个复合字段拆出地区、年份 | OP4 | 单元格内部字段解析 |

操作根据期望输出标注，不能因为代码调用了 `concat`、`merge_cells` 或 `split` 就自动选择 OP6。
横向整合通常使用 J1–J4 按键匹配；不默认把两个表当前行位置视为同一记录。
若按共同记录序号对齐，必须给出稳定身份/顺序约定并校验缺行、重复和错序。
只有在独立需要改变层级表示时另标 OP7；单纯存在合并单元格是 S3 输入属性。

## 2. 子类型

| 子型 | 目标 | 必须明确与核验 |
|---|---|---|
| J1 单键一对一关联 | 两表按一个键关联 | 左右键唯一性、连接类型、未匹配与空键 |
| J2 单键一对多/多对一 | 明细与主表/子表关联 | 基数、重复来源记录的保留次数 |
| J3 单键多对多 | 同键出现多个记录 | 每个键的预期配对次数，禁止意外笛卡尔扩张 |
| J4 多键关联 | 按地区×年份等复合键匹配 | 完整复合键；另填 cardinality |
| J5 纵向合并 Append Rows | 多个表对齐字段后追加记录 | 列映射、Schema 策略、缺列、重复、顺序 |
| J6 按行拆表 Partition Rows | 按字段/规则分配至多个输出表 | 路由、完整覆盖、重叠及未归属记录 |
| J7 按列拆表 Split Columns | 共享身份键，按字段组拆表 | 键保留、非键字段不丢失不重复、重组规则 |

子型选择顺序：多键关联优先 J4，基数独立记录；单键关联再按 J1/J2/J3 选择。
这避免把“多键”和“多对多”误当成互斥概念。J5–J7 不借用 join 的空键/连接语义。

## 3. 指令契约和 Metadata

所有 OP6 节点必须有 `subtype` 和 `table_contract`，Schema 强制检查其与 `kind` 一致。
`operation_nodes` 不暴露给执行 Agent；Agent 只接收任务输入和当前指令。

共同字段：

- `kind`：`join`、`append_rows`、`partition_rows`、`split_columns`。
- `input_tables`、`output_tables`：本 Case 内唯一逻辑表标识。来源路径、sheet/数据块定位另在 Metadata 解释。
- `duplicate_policy`、`null_policy`、`order_policy`：明确重复、空值及顺序的业务语义；顺序不限定时写明按多重集合等价。

各类附加字段：

- Join：`keys`（逐对 left/right 字段）、`join_type`、`cardinality`、`unmatched_policy`。
- J5：`column_alignment`、`schema_policy`、`missing_column_policy`；显式映射时另给 `column_mapping`。
  支持严格同 Schema、字段并集、字段交集、显式映射。字段交集会丢弃列，必须在指令中明确授权丢弃哪些信息。
  同名不同单位不能直接合并；若需要转换字段值，另标 OP5 并明确规则。
- J6：`partition_keys`、`routing_policy`、`row_coverage`、`unassigned_policy`。
  默认采用 `exactly_once`，每条输入出现一次且只有一个去向；确需重叠时使用 `specified_overlap` 并写 `overlap_policy`。
  输出 sheet 的命名、顺序、空分区处理与非法名称转换必须可确定。
- J7：`key_columns`、`source_columns`、`column_groups`、`reconstruction_policy`。
  `column_groups` 按输出表名列出非键字段，所有源字段恰由公共键和这些字段组覆盖。
  共同键必须能识别记录；非唯一业务键需要已有记录 ID，或另行声明并标注生成 ID 的规则，不能静默去重。

Schema 校验字段完整性和子型边界；`validate_annotations.py` 另查 J7 的字段遗漏、重复、输出表未映射及重复 Join 键字段。
这些是标注前置检查，不能替代工作簿级验证器；字段实际存在、键唯一性和结果事实仍需对输入/Gold 独立核验。

## 4. Gold 和错误注入

| 类型 | 正确性不变量 | 必须拒绝的反例 |
|---|---|---|
| Join | 键配对正确；每键输出基数符合约定；保留源记录出现次数 | 漏一维键、错 Join 类型、空键误匹配、重复键意外扩张 |
| J5 | 每个保留字段映射正确；输出记录数/多重集合符合追加策略 | 按列位置拼接错字段、静默去重、缺列填零、未经授权截取交集 |
| J6 | 记录按规则归属；exactly_once 时各输出合计还原输入多重集合 | 丢一行、重复分配、错分区、把空键记录静默丢弃 |
| J7 | 所有字段和身份键保留；按约定键重组后还原输入事实 | 丢列、非键列重复、缺公共键、非唯一键重组产生多对多扩张 |

验收必须同时包含正例与负例。记录以带重复次数的多重集合比较，不能用 set 隐藏重复。
正例包括列位置变化、不同但语义等价的布局和纯字体/颜色变化。
负例应一次改变一个因素，使失败可解释；不能把多种错误同时注入后声称每一种都已验证。

拆分与重新合并的 round-trip 是额外一致性证据；还需校验分区/字段归属正确，
因为“分错但能重新拼回”仍可能违反任务。关联任务以独立键配对/基数核验为主，不能只比较一个总和。

## 5. 更有挑战的构造方向

1. **多键 + 重复/未匹配**：多期间、同名产品，包含合法重复明细、未匹配主表记录和显式空键策略。
2. **列顺序变化 + 部分缺列**：多个来源字段顺序不同；限定可接受的列别名、缺列补空和重复保留规则。
3. **拆表覆盖 + 非唯一业务标签**：相同显示名称对应不同记录 ID；要求正确分区并可按 ID 重组。
4. **真实依赖组合**：OP4 拆出地区/年份 → OP6 J4 关联分类 → OP3 按关联分类生成统计行。
   或 OP7 展开输入语义表头 → OP6 J5 整合 → OP6 J6 分区；每条边必须对应可观察的数据依赖。
5. **布局/规模对照**：保持业务事实与规则一致，改变数据块位置、列序和规模，单独报告鲁棒性。

优先从独立真实来源构建任务；同一源表的合并/拆分变体共享 `source_family_id`，不能跨正式 split。
扩展子型本身不等于已有数据变难。新增任务仍须来源/许可审核、独立 Gold、唯一可判定指令及错误注入。
